### 3. R²(결정계수) 값을 99% 이상에서 더 완벽하게 높일 방법은?
현재도 R² 값이 0.98~0.99 수준으로 매우 높지만, 이를 더 한계점까지 끌어올리기 위한 **고급 파이프라인 전략**은 다음과 같습니다:

1.  **하이퍼파라미터 튜닝 (GridSearchCV / Optuna)**
    *   현재는 기본(Default) 옵션으로 100개의 트리(`n_estimators=100`)만 생성했습니다. 딥러닝처럼 트리의 깊이(max_depth), 학습률(learning_rate) 등 최적의 조합을 탐색하면 0.001 단위의 R² 점수를 쥐어짤 수 있습니다.
2.  **교차 검증 (K-Fold Cross Validation)**
    *   단순히 70:30으로 1번만 테스트한 현재와 달리, 5-Fold 기법을 사용해 데이터를 5조각으로 내서 검증하면, 특정 테스트 셋에만 우연히 잘 맞는(Overfitting) 현상을 방지해 줍니다.
3.  **파생 변수(Feature Engineering) 생성**
    *   반도체 공정 특성 상 "빛의 에너지"와 "초점"이 결합될 때 불량이 폭증합니다. 즉, 단순히 `Dose` 피처와 `Focus` 피처를 각각 두는 대신, `Dose × Focus`나 `Dose / Coat_Thickness` 같은 **상호작용(Interaction) 파생 변수**를 만들어서 모델에 던져주면 복잡한 비선형 관계를 훨씬 더 잘 포착할 수 있습니다.
4.  **고립된 미세 이상치(Outlier) 추가 제거**

### 🚀 성능 향상을 위해 방금 적용한 최적화 기법
1.  **파생 변수 추가 (Polynomial Features)**: 단순히 노광량(Dose)과 초점(Focus)을 개별적으로 넣는 것을 넘어, 공학적으로 큰 영향을 미치는 `Dose²`이나 `Dose × Focus` 같은 2차항 상호작용 피처를 알고리즘이 직접 학습하도록 추가했습니다.
2.  **하이퍼파라미터 튜닝 (GridSearchCV)**: 3-Fold 교차 검증을 통해 트리의 깊이(max_depth), 학습률(learning_rate) 등의 파라미터 조합을 탐색하여 최적의 XGBoost 및 Random Forest 세팅을 찾았습니다.

*   **Negative PR (XGBoost)**: R² `0.5807` ➡️ **`0.5244` (오히려 과적합 발생)**

### 💡 R² 값을 90% 이상으로 높이는 것이 어려운 이유 (실무적 한계)
튜닝을 통해 Positive 데이터는 약 86%까지 설명력을 끌어올렸지만, 여전히 95%~99%에 도달하지 못하는 데에는 현업 반도체 공정 데이터의 본질적인 이유가 있습니다.
1.  **관측되지 않은 잠재 변수(Latent Variables)**: 현재 데이터에는 설비 내부의 미세한 진동, 렌즈 수차, 챔버 내 온도 불균형 등 CD(선폭)에 영향을 주는 수많은 환경 노이즈가 포함되어 있지 않습니다. 모델은 주어진 센서 데이터 안에서만 예측하므로 물리적 노이즈를 완벽히 통제할 수 없습니다.
2.  **Negative PR 데이터의 한계**: Negative 그룹은 Positive에 비해 데이터 수가 적고 노이즈가 강해, 파생 변수를 추가했음에도 오히려 훈련 데이터에 과적합(Overfitting)되어 검증 점수가 떨어지는 모습을 보였습니다.

**결론적으로:** 
현업 공정 데이터 관점에서는 **설비 파라미터(Dose, Focus 등)만으로 86%의 CD 분산을 예측(Positive 기준)해 낸 것은 꽤 유의미한 수치**입니다. 만약 R²를 90% 이상으로 극적으로 높이려면, 딥러닝(MLP)을 도입하기보다는 모델에 주입되는 원본 데이터 자체에 **계측기의 계측 오차 보정**이나 **설비의 물리적 상태(Log) 피처**를 새롭게 추가하는 Feature Engineering 작업이 선행되어야 합니다!

이 정확도는 미지의 Holdout 데이터를 평가한 것이 아니라, **이미 정답을 알고 있는 기존 학습 데이터(`train_cleaned.csv`)를 이용해 치르는 '모의고사' 성적**입니다. 이를 머신러닝에서는 **교차 검증(Cross-Validation)**이라고 부릅니다.

원리는 다음과 같습니다.

### 📊 5-Fold 교차 검증(Cross-Validation)의 원리
1. **데이터 쪼개기**: 정답(`spec_pass`)이 포함되어 있는 기존 Positive PR 데이터(약 380개)를 무작위로 **5조각(Fold)**으로 똑같이 나눕니다.
2. **학습과 시험의 반복 (5번)**:
   - **1회차**: 1~4번 조각으로 인공지능을 학습시키고, 학습에 쓰지 않은 **5번 조각**으로 시험을 쳐서 정확도를 구합니다.
   - **2회차**: 1, 2, 3, 5번 조각으로 학습시키고, **4번 조각**으로 시험을 칩니다.
   - 이런 식으로 시험을 치는 조각을 바꿔가며 **총 5번의 시험**을 봅니다.
3. **평균 내기**: 5번의 시험에서 나온 정확도(예: 81%, 78%, 80%, 79%, 81%)를 **평균 낸 값**이 바로 리포트에 적힌 **79.96%**입니다.

### 💡 결론
즉, 79.96%라는 정확도는 **"이 분류 모델은 자신이 한 번도 본 적 없는 낯선 공정 데이터를 만났을 때, 대략 10번 중 8번 꼴로 합격/불합격을 정확하게 맞추는 실력을 가졌다"**라는 수학적 보증 수표(검증 결과)입니다. 

우리는 이 모의고사 성적을 바탕으로, 이 모델이 정답이 없는 `A_holdout_features.csv` 실전 데이터에서도 약 80% 수준의 신뢰도로 불량을 솎아낼 것이라고 합리적으로 추론(예측)할 수 있습니다!

[AI 어시스턴트 답변]
보고서에 적힌 **Acc**와 **F1**은 인공지능이 정답을 얼마나 잘 맞추는지 평가하는 채점 기준(지표)입니다.

쉽게 비유해서 설명해 드릴게요.

### 1. Acc (Accuracy, 정확도)
**"전체 문제 중에서 몇 개나 맞췄는가?"**
- 예를 들어 100개의 반도체 칩이 있을 때, AI가 합격/불합격을 총 80개 맞췄다면 정확도는 80%입니다.
- **단점**: 만약 원래 데이터의 90%가 '불합격'인 극단적인 상황이라면, AI가 아무 생각 없이 "전부 다 불합격!"이라고 찍기만 해도 정확도가 90%로 나옵니다. 이를 이른바 '가짜 정확도'라고 합니다.

### 2. F1 (F1-Score, 에프원 점수)
**"한쪽으로 치우치지 않고 균형 있게 잘 맞추었는가?"**
- 위에서 말한 '가짜 정확도'의 함정에 빠지지 않기 위해 보는 지표입니다.
- AI가 **PASS를 맞추는 실력**과 **FAIL을 맞추는 실력**을 모두 종합해서 0점부터 100점(또는 0.0 ~ 1.0) 사이로 매긴 **종합 점수**입니다.
- 데이터 불균형이 있을 때 진짜 모델의 성능을 보려면 반드시 이 F1 점수를 봐야 합니다.

- **영향:** Negative PR 모델은 "Dose가 오르면 CD도 커진다"고 학습해야 하는데, 이 데이터 하나가 "아닌데? 작아지는데?"라며 모델의 회귀선(학습 방향)을 반대로 꺾어버리는 엄청난 악영향을 미칩니다.
- **처리 방법:** **무조건 삭제(Drop)해야 합니다.** 현업에서는 이를 '도메인 지식을 활용한 Hard Filtering'이라고 부르며, Positive 데이터셋으로 옮겨주기보다는 원인 불명의 데이터로 간주하고 삭제하는 것이 가장 안전합니다.

### 2. 허용 공차를 아득히 벗어난 데이터 (Dose 79.1, CD 66.31) 처리
- **현상:** Dose(79.1)는 정상 범주인데 결과물인 CD만 66nm로 비정상적으로 튀었습니다. (보통 해당 Dose에서는 48~51nm가 정상)
- **영향:** 분류(PASS/FAIL) 모델 입장에서는 어차피 FAIL이므로 큰 문제가 없지만, **CD 값을 정확히 맞춰야 하는 회귀(Regression) 모델 입장에서는 이 점 하나 때문에 전체 오차(MSE)가 폭등**하여 다른 정상 웨이퍼들의 예측력까지 깎아먹습니다.
- **처리 방법:** Target 변수(CD)에 대해 **IQR(사분위수 범위) 기반의 이상치 제거 기법**을 적용하여 잘라냅니다. 보통 $Q_3 + 1.5 \times IQR$ 을 초과하는 데이터는 계측기 에러(Metrology Glitch)로 간주하고 모델 학습(Train) 단계에서 배제하는 것이 좋습니다.
